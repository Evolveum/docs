= MidPilot AI services setup
:page-nav-title: AI setup
:page-display-order: 80
:page-toc: top
:page-keywords: connector generator, identity connectors, connectors, ai, midpilot, llm, api key, container images
:page-description: Setup of midPilot AI services for midPoint: Evolveum-hosted service or self-hosted deployment

MidPilot is a set of AI-assisted features that extend core identity management capabilities of midPoint and enable fast onboarding of applications for which no suitable connector exists.

MidPilot features are provided by microservices that use a large language model (LLM).
The microservices are available either as a service hosted by Evolveum, including the LLM, or for self-hosted deployment connected to any OpenAI-compatible LLM provider.
This article describes the architecture and requirements of midPilot and how to set up either option.

== Introduction

MidPilot consists of two independent microservices:

midpilot-smart-integration ::
    Generates configuration suggestions for resource object types, inbound/outbound mappings, delineation, synchronization, and correlation rules.
    Uses midPoint schema information as context. +
    link:https://github.com/Evolveum/midpilot-smart-integration[Smart integration microservice repository on GitHub]
midpilot-connector-gen ::
    Generates connector code for a target application by analyzing API documentation of the application retrieved from the Internet.
    Requires its own PostgreSQL database and access to a search engine.
    MidPoint builds the generated connector on top of connector framework template JAR files. +
    link:https://github.com/Evolveum/midpilot-connector-gen[Connector generator microservice repository on GitHub]

Both services use a LLM for certain parts of their operations.
Hence the "AI-assisted" term.
Both services have been production-ready since their 1.0.0 release in October 2026.

Both services are optional and not essential for midPoint itself to function.
Either service can be used independently of the other.
At the same time, the services are not enabled out of the box in a _default_ midPoint installation.
MidPoint must be explicitly configured to use them, either with the Evolveum-hosted service or with a self-hosted deployment;
this article is a reference for such configuration.

MidPoint itself does not communicate directly with the LLM.
Instead, it delegates the communication to the microservices, which call the LLM via an OpenAI-compatible Chat Completions API.

== Prerequisites

This section covers the basic requirements for deployment of midPilot AI services.

=== MidPoint version

MidPilot integration requires *midPoint 4.11 or later*.
See, for example, the link:https://hub.docker.com/r/evolveum/midpoint/tags?name=4.11[Docker Hub midPoint 4.11 tags].

[[llm-provider]]
=== LLM provider

The link:#evolveum-hosted[Evolveum-hosted service] requires no separate LLM.
Evolveum runs the microservices together with its own self-hosted LLM infrastructure (the *gpt-oss-120b* model).

Self-hosted microservices require an LLM endpoint
that is compatible with the link:https://developers.openai.com/api/reference/chat-completions/overview[OpenAI Chat Completions API].
OpenAI itself is not required—any OpenAI-compatible provider or proxy works.

.Be wary of public LLM services
[NOTE]
====
Although a public LLM can be used with midPilot,
it comes with risks.
External LLMs outside of the organization's control may store the data sent to them and use them for training,
potentially exposing sensitive information.

We strongly suggest using self-hosted LLMs which are fully under the organization's control,
or the Evolveum-hosted service, which uses Evolveum's own self-hosted LLM.
====

[[required-config-vars]]
Configuration of either microservice requires the following information from the LLM provider:

[cols="1,5", options="header"]
|===
|Environment variable |Description
|`LLM__OPENAI_API_BASE`
|Base URL of the OpenAI-compatible API endpoint. +
    Defaults to `\https://openrouter.ai/api/v1` (OpenRouter).
|`LLM__MODEL_NAME`
|Model identifier. +
    The defaults differ: the connector generator uses `openai/gpt-oss-120b`, the smart resource integration service uses `openai/gpt-oss-20b`.
    Set the value explicitly for both services. +
    Based on our analysis, *gpt-oss-120b* has proven to be the most effective so far.
    Pay attention to naming conventions—some providers prefix model names (e.g., `openai/gpt-oss-120b`).
    Consult the documentation of the LLM provider.
|`LLM__OPENAI_API_KEY`
|API key for the LLM endpoint, sent as a Bearer token
|===

=== Internet access

The connector generator microservice requires Internet access in order to:

* Search for API documentation of the target application (via Brave Search or DuckDuckGo).
* Download and process the documentation pages.
    The microservice uses a headless Chromium browser for this.

MidPoint itself downloads the link:#connector-framework-jar[connector framework template JAR files] from the Evolveum Nexus repository when it creates a connector, unless a local `file://` path is configured.

Additionally, both microservices require network connection to call the LLM API.
If the LLM does not run within the same network perimeter, the smart resource integration service requires Internet connection as well.

With the Evolveum-hosted service, midPoint needs outbound HTTPS access to `midpilot-api.evolveum.com` and to the Evolveum Nexus repository.

If the deployment environment restricts Internet access, see the link:#corporate-proxy-environments[Corporate proxy environments] section below.

=== PostgreSQL

_Self-hosted deployments only._

The connector generator microservice requires a *dedicated PostgreSQL database* (PostgreSQL 15 or later) for storing indexed documentation chunks, sessions, jobs, and LLM query optimization metadata.
The database must exist and be accessible before the service starts because the link:#database-migrations[database migration] has to run before the API server is launched.

[NOTE]
====
Use a separate PostgreSQL instance for the connector generator.
While it may be technically possible to share the main midPoint repository database, doing so risks namespace collisions between the midPoint schema and the connector generator database schema.
====

[[langfuse]]
=== Langfuse tracing (optional)

_Self-hosted deployments only._

link:https://github.com/langfuse/langfuse[Langfuse] is an AI engineering platform that helps debug and analyze LLM applications.
It is used purely for tracking LLM calls made by the microservices and it is not required for midPilot microservices or midPoint to function.

Langfuse tracing is enabled by setting `LANGFUSE__TRACING_ENABLED` to `true`.

*LLM call tracing is disabled by default*.
Langfuse is not part of midPilot; it has to be deployed and configured separately according to the official https://langfuse.com/docs[Langfuse documentation].

With tracing enabled, the remaining Langfuse variables must be configured in the `.env` file of each service:

[cols="2,5", options="header"]
|====
|Environment variable | Description
|`LANGFUSE__HOST` | Service host
|`LANGFUSE__SECRET_KEY` | Secret key of the Langfuse API
|`LANGFUSE__PUBLIC_KEY` | Public key of the Langfuse API
| `LANGFUSE__ENVIRONMENT` | Label assigned to all traces sent to Langfuse. See below.
| `LANGFUSE__CA_CERT_FILE` | Optional path to certificate for securing communication with the service
|====

==== Langfuse environment label

This setting is used exclusively for observability and trace organization.
It does not affect application behavior, LLM calls, database operations, or which endpoints are traced.

Purpose ::
    The environment label can be used to filter and segment traces in the Langfuse UI.
    This is particularly important when multiple application environments send traces to the same Langfuse project.
    For example, it makes it possible to distinguish production and staging traces from local development runs.
    Without a unique environment label, traces from all application instances are displayed together in the same project.

Recommended values ::
    * `production`
    * `development`
    * developer's name for testing and development +
        Each developer should use a unique `dev-<name>` value.
        Otherwise, local traces generated by different developers cannot be reliably distinguished.

[[evolveum-hosted]]
== Evolveum-hosted midPilot service

Evolveum runs both midPilot microservices in production, together with the LLM they use.
This is the fastest way to start with midPilot: no deployment is needed, midPoint only connects to the service with an API key.

[cols="1,3", options="header"]
|===
|Microservice |URL
|Smart resource integration
|`\https://midpilot-api.evolveum.com/midpilot-smart-integration/`
|Connector generator
|`\https://midpilot-api.evolveum.com/midpilot-connector-gen/api/v1`
|===

To connect midPoint to the hosted service:

. Create an API key in the Integration catalog.
    See xref:/connectors/integration-catalog/catalog-settings/#api-keys[Integration catalog API keys]. +
    API keys expire.
    Rotate the key before it expires and update it in midPoint.
    The linked page describes the expiration and rotation rules.
. In midPoint, go to *System* -> *Smart integration* and fill in the service URLs above and the API key.
    Use the same API key for both microservices.
. Verify the connection, see link:#verification-checklist[Verification checklist].

MidPoint sends the API key with every request to the microservices.
The key also identifies the owner of connector generation sessions:
sessions created with one key are not accessible with another key.
This also applies to a rotated key.
Finish running connector generation sessions before rotating the key, or start them again with the new key.

[[smart-resource-integration-microservice]]
== Smart resource integration microservice

This section describes the self-hosted deployment of the smart resource integration microservice (`midpilot-smart-integration`).
It does not apply to the link:#evolveum-hosted[Evolveum-hosted service].

The microservice provides AI-assisted suggestions for:

* Resource object type configuration
* Inbound and outbound mapping rules
    ** Mapping suggestions are generated on demand using midPoint schema information as context.
* Delineation
* Synchronization rules
* Correlation rules
    ** Requires related shadow objects to be present in midPoint.


=== Requirements

* Accessible LLM endpoint
* Network connectivity between midPoint and the microservice

No additional database is required.

=== Deployment

Deploy the `midpilot-smart-resource-integration` container (e.g., via Kubernetes, Docker Compose, Nomad job, etc.).
The service listens on *port 8090* by default.
MidPoint communicates with the microservice using REST API over HTTP.
`GET /health` is a liveness check without dependencies, suitable for container health probes.

For example, with Docker, put the configuration into an environment file:

.midpilot-smart-integration.env
[source]
----
LLM__OPENAI_API_BASE=https://llm.example.com/v1
LLM__OPENAI_API_KEY=<LLM API key>
LLM__MODEL_NAME=gpt-oss-120b
LLM__PROVIDER_NAME=my-llm
----

and start the container:

[source,bash]
----
docker run -d --name midpilot-smart-integration \
  --env-file midpilot-smart-integration.env \
  -p 8090:8090 \
  midpilot-smart-integration:1.0.1
----

The microservice has no authentication of its own.
Make sure that only midPoint can reach it, or put an API gateway in front of it.
If the gateway requires an API key in the `X-Gravitee-Api-Key` HTTP header, set it in `serviceApiKey` in the link:#midpoint-configuration[midPoint configuration].

A demo Docker Compose file is available at link:https://github.com/Evolveum/midpoint-samples/blob/master/samples/demo/smart-resource-integration/docker/smart-resource-integration/docker-compose.yml[Evolveum midpoint-samples GitHub repository].
The demo uses the floating `smart-integration-demo` image tag;
for production, pin a release tag such as `1.0.1`, as in the example above.

=== Environment variables

Beside the link:#required-config-vars[required configuration variables] and the link:#langfuse[optional Langfuse service connection setup], the following variables are available:

[cols="3,2,4", options="header"]
|===
|Environment variable |Default |Description
|`LOGGING__LEVEL`
|`info`
|Logging level (e.g., `debug`, `info`, `error`, `warning`, `critical`)
|`LLM__EXTRA_BODY`
|OpenRouter provider routing
|JSON object added to the body of every LLM request.
    The default contains OpenRouter-specific provider preferences.
    *Set it to `{}` for any other provider.*
|`LLM__PROVIDER_NAME`
|`openrouter`
|Name of the LLM provider shown in health and status messages.
    Set it to the name of the LLM provider in use.
|`LLM__REQUEST_TIMEOUT`
|`120`
|Timeout of the whole LLM call, in seconds
|`LLM__REASONING_EFFORT`
|`high`
|Reasoning effort for models that support it: `low`, `medium`, or `high`
|`LLM__CA_CERT_FILE`
|none
|Path to a CA certificate file, if the LLM endpoint uses a certificate signed by an internal certificate authority
|===

=== Recommended pre-deployment checks

1.  Verify the LLM endpoint is reachable by the microservice.
2.  Verify network connectivity between midPoint and the microservice.
3.  Perform a simple runtime test with a dummy CSV resource.

== Connector generator microservice

This section describes the self-hosted deployment of the connector generator microservice (`midpilot-connector-gen`).
For the link:#evolveum-hosted[Evolveum-hosted service], only the link:#connector-framework-jar[Connector framework JAR] and link:#demo-target-application[Demo target application] sections apply.

The microservice generates connector code for target applications by:

. Searching for and downloading API documentation of the target application
. Indexing documentation chunks in PostgreSQL
. Using LLM-assisted analysis to produce connector code based on a connector framework template (SCIM/REST or SQL)

=== Requirements

* Accessible LLM endpoint
* Dedicated PostgreSQL 15 or later database (must exist before startup)
* Internet access for documentation discovery
* Search engine access: Brave Search API key (recommended for better search quality) or DuckDuckGo
* An API gateway or a network restriction so that only midPoint can reach the service (see link:#authentication[Authentication])

=== Components

The microservice consists of two parts:

* `midpilot-connector-gen`: the API server, which also runs the background jobs
* PostgreSQL database

=== Deployment

. Create the PostgreSQL database and a user for the microservice.
. Run the link:#database-migrations[database migration].
. Start the `midpilot-connector-gen` container (e.g., via Kubernetes, Docker Compose, Nomad job, etc.).

The service listens on *port 8090* by default.
MidPoint communicates with the microservice using REST API over HTTP.

For example, with Docker, put the configuration into an environment file:

.midpilot-connector-gen.env
[source]
----
LLM__OPENAI_API_BASE=https://llm.example.com/v1
LLM__OPENAI_API_KEY=<LLM API key>
LLM__MODEL_NAME=gpt-oss-120b
SEARCH__METHOD_NAME=brave
BRAVE__API_KEY=<Brave Search API key>
AUTH__MODE=prod
DATABASE__URL=postgresql+asyncpg://midpilot:<password>@postgres.example.com:5432/midpilot_connector_gen
----

Docker environment files do not expand variables, so write `DATABASE__URL` in full.
Then run the database migration and start the container:

[source,bash]
----
docker run --rm --env-file midpilot-connector-gen.env \
  midpilot-connector-gen:1.0.1 \
  alembic upgrade head

docker run -d --name midpilot-connector-gen \
  --env-file midpilot-connector-gen.env \
  -p 8090:8090 \
  midpilot-connector-gen:1.0.1
----

The link:https://github.com/Evolveum/midpilot-connector-gen/blob/main/docker-compose.yaml[Docker Compose file in the repository] shows how to run the microservice together with PostgreSQL.

[[database-migrations]]
=== Database migrations

The container starts only the API server (`python server.py`); it does not migrate the database.
Run `alembic upgrade head` with the same image and the same configuration:

* before the first start,
* after every upgrade to a newer image, before the new version starts.

In Kubernetes, the migration can run in an init container of the microservice pod.
With more than one replica, run the migration once (e.g., as a separate job), not in every replica at the same time.

Back up the database before upgrading to a version that contains new migrations.
Rolling back to an older image is safe only if the older version supports the current database schema.

[[authentication]]
=== Authentication

By default, the microservice runs with `AUTH__MODE=prod`:

* Every `/api/v1` request must contain exactly one `X-Gravitee-Api-Key` HTTP header, otherwise the service responds with HTTP 401.
    MidPoint sends this header when `connectorGeneratorApiKey` is set in the link:#midpoint-configuration[midPoint configuration].
* The key identifies the owner of sessions and cached results.
    Different keys cannot access each other's sessions.
    A rotated key is a different owner, so sessions of the old key are not accessible with the new one.

[IMPORTANT]
====
The microservice does not validate the key itself; it trusts the header.
Therefore, do one of the following:

* Put the microservice behind an API gateway that validates the keys and forwards the validated key in the `X-Gravitee-Api-Key` header.
    Make sure the microservice cannot be reached other than through the gateway.
* Restrict network access so that only midPoint can reach the microservice, and set a random, high-entropy key in `connectorGeneratorApiKey`.
====

`AUTH__MODE=dev` disables authentication and session isolation.
Use it only for local development, never for a shared deployment.

The `/health`, `/docs`, `/redoc` and `/openapi.json` endpoints are not authenticated.

=== Health and readiness endpoints

`GET /health` ::
    Liveness check without dependencies and without authentication.
    Use it for container health probes.
`GET /api/v1/ready` ::
    Readiness check for API clients, such as midPoint.
    It requires authentication like every other `/api/v1` endpoint.
    It checks the database and the LLM endpoint and returns HTTP 503 with the result of each check if a dependency is unavailable.
    The LLM check calls `GET /models` on the LLM endpoint and consumes no tokens, so the LLM endpoint must support it.

[[connector-framework-jar]]
=== Connector framework JAR

When midPoint creates a generated connector, it builds the connector on top of a connector framework template JAR file (one layer above ConnId).
MidPoint downloads the template from the URL configured in the link:#midpoint-configuration[midPoint System configuration object]:

* `connectorFrameworkUrl` for SCIM and REST connectors
* `connectorSqlFrameworkUrl` for SQL connectors

MidPoint 4.11 ships with default values that point to the template versions released together with midPoint in the link:https://nexus.evolveum.com/[Evolveum Nexus repository]:

* `+https://nexus.evolveum.com/nexus/repository/releases/com/evolveum/polygon/scimrest/connector-scimrest-template/0.2.0-RC2/connector-scimrest-template-0.2.0-RC2.jar+`
* `+https://nexus.evolveum.com/nexus/repository/releases/com/evolveum/polygon/sql/connector-sql-template/0.2.0-RC2/connector-sql-template-0.2.0-RC2.jar+`

Change these values only when necessary.
For example, if network access to Nexus is restricted, download the JAR files and use a local `file://` path instead of the HTTP URL.

=== Recommended pre-deployment checks

. Verify the LLM endpoint is reachable and the LLM API key is valid.
. Verify PostgreSQL connectivity, that the database exists, and that the migration has run.
. Verify search engine access and configuration (DuckDuckGo or Brave, depending on configuration).
. Verify that midPoint can access Nexus or the local path for the connector framework JAR files.
. Test connectivity between midPoint and the connector generator service.
. Perform a runtime test: create a SCIM connector targeting link:https://scim.dev/[`scim.dev`] (search for documentation and generate a connector).

[[midpoint-configuration]]
== MidPoint configuration

Once the microservices are available, configure midPoint to connect to them.
This is done in the `smartIntegration` block within the midPoint System configuration object.
It can be edited in the GUI in *System* -> *Smart integration*, or directly in XML.

The configuration block is present in the System configuration object out of the box, including the default connector framework URLs.
Only the service URLs and, if needed, the API keys have to be added.

Example for the Evolveum-hosted service:

[source,xml]
----
<smartIntegration>
    <!-- Smart resource integration service -->
    <serviceUrl>https://midpilot-api.evolveum.com/midpilot-smart-integration/</serviceUrl> <1>
    <serviceApiKey>
        <t:clearValue>integration-catalog-api-key</t:clearValue> <2>
    </serviceApiKey>

    <!-- Connector generator service -->
    <connectorGenerationUrl>https://midpilot-api.evolveum.com/midpilot-connector-gen/api/v1</connectorGenerationUrl> <3>
    <connectorGeneratorApiKey>
        <t:clearValue>integration-catalog-api-key</t:clearValue> <2>
    </connectorGeneratorApiKey>

    <!-- Connector framework templates (defaults shipped with midPoint) -->
    <connectorFrameworkUrl>https://nexus.evolveum.com/nexus/repository/releases/com/evolveum/polygon/scimrest/connector-scimrest-template/0.2.0-RC2/connector-scimrest-template-0.2.0-RC2.jar</connectorFrameworkUrl> <4>
    <connectorSqlFrameworkUrl>https://nexus.evolveum.com/nexus/repository/releases/com/evolveum/polygon/sql/connector-sql-template/0.2.0-RC2/connector-sql-template-0.2.0-RC2.jar</connectorSqlFrameworkUrl> <4>

    <!-- Timeouts -->
    <connectorGenerationTransientErrorTimeout>PT15S</connectorGenerationTransientErrorTimeout> <5>
    <serviceResponseTimeout>PT2M</serviceResponseTimeout> <6>

    <!-- Shared settings -->
    <statisticsTtl>P1D</statisticsTtl> <7>
    <schemaMatchTtl>P1D</schemaMatchTtl> <8>
    <mappingSuggestionRetryCount>1</mappingSuggestionRetryCount> <9>
</smartIntegration>
----
<1> Base URL of the smart resource integration microservice, *without* `/api/v1`.
<2> API key sent with every request to the microservice in the `X-Gravitee-Api-Key` HTTP header.
<3> URL of the connector generator microservice API, *including* `/api/v1`.
<4> URL or local `file://` path to the link:#connector-framework-jar[connector framework template JAR] for SCIM/REST and SQL connectors
<5> How long midPoint tolerates transient gateway errors (HTTP 502 and 504) while monitoring connector generation jobs before it declares the operation failed (default: 15 seconds)
<6> Maximum time to wait for a response from the smart resource integration microservice (default: 2 minutes)
<7> Time-to-live for cached statistics data (ISO 8601 duration, e.g., P1D = 1 day)
<8> Time-to-live for cached schema matching results (ISO 8601 duration)
<9> Number of retry attempts for mapping suggestions when validation fails (default: 1; 0 = no retries)

A self-hosted deployment uses its own addresses:

[cols="2,3,3", options="header"]
|===
|Element |Evolveum-hosted service |Self-hosted deployment (example)
|`serviceUrl`
|`\https://midpilot-api.evolveum.com/midpilot-smart-integration/`
|`\http://midpilot-smart-integration:8090/`
|`serviceApiKey`
|Integration catalog API key
|Only if the API gateway requires a key
|`connectorGenerationUrl`
|`\https://midpilot-api.evolveum.com/midpilot-connector-gen/api/v1`
|`\http://midpilot-connector-gen:8090/api/v1`
|`connectorGeneratorApiKey`
|Integration catalog API key (the same as for `serviceApiKey`)
|Required with `AUTH__MODE=prod`, see link:#authentication[Authentication]
|===

== Addendum

=== Deployment considerations

Network ::
    The microservices communicate with midPoint using REST API over HTTP.
    Ensure the network policies permit such communication.
    For the Evolveum-hosted service, midPoint needs outbound HTTPS access to `midpilot-api.evolveum.com`.
Authentication ::
    The Evolveum-hosted service requires an API key from the Integration catalog.
    In a self-hosted deployment, the smart resource integration microservice has no authentication of its own,
    and the connector generator expects an API key that an API gateway in front of it has validated.
    See link:#authentication[Authentication].
Secrets management ::
    API keys (LLM, Brave search, midPilot), database passwords, and other sensitive values should be injected through a secret vault (e.g., Kubernetes Secrets), not hardcoded in deployment manifests.
Logs ::
    The midPoint-side logging module for the midPilot microservices is `com.evolveum.midpoint.smart.impl`.

[[corporate-proxy-environments]]
=== Corporate proxy environments

If the deployment sits behind a corporate proxy, additional configuration is needed:

* *Microservices* inherit proxy configuration from the operating system (standard `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` environment variables).
    Add internal hosts, such as a self-hosted LLM endpoint, to `NO_PROXY` if they are not reachable through the proxy.
* *MidPoint (Java)* additionally requires JVM proxy properties. +
    Container proxy variables alone are *not sufficient* for outbound HTTP communication initiated by Java.
    The following properties must be set:
    ** `http.proxyHost`
    ** `http.proxyPort`
    ** `https.proxyHost` (if applicable)
    ** `https.proxyPort` (if applicable)

These configuration options are typically passed as JVM arguments (e.g., `‑Dhttp.proxyHost=proxy.example.com ‑Dhttp.proxyPort=8080`). +
We suggest using the `MP_SET` environment variables, such as:

* `MP_SET_http_proxyHost`
* `MP_SET_http_proxyPort`
* `MP_SET_http_proxyUser`
* `MP_SET_http_proxyPassword`
* `MP_SET_http_nonProxyHost`
* And their `https` counterparts if applicable

If the proxy or the LLM endpoint uses certificates signed by an internal certificate authority, configure the CA certificate file in the microservices:

* `LLM__CA_CERT_FILE` for the LLM endpoint
* `LANGFUSE__CA_CERT_FILE` for Langfuse, if used
* `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` for the other outbound HTTPS calls

The headless Chromium browser that the connector generator uses to download documentation uses the proxy settings but not these CA variables.
Downloading documentation through a TLS-inspecting proxy may therefore fail.

[[verification-checklist]]
=== Verification checklist

Use these checklists after deployment to confirm everything works correctly.

* *Evolveum-hosted service*
    ** `serviceUrl` and `connectorGenerationUrl` in System configuration exactly match the URLs in the link:#evolveum-hosted[Evolveum-hosted midPilot service] section.
    ** `serviceApiKey` and `connectorGeneratorApiKey` contain a valid, unexpired API key from the Integration catalog.
    ** MidPoint can reach `midpilot-api.evolveum.com` over HTTPS (check the proxy configuration, if applicable).
    ** Verification of the API key:
+
[source,bash]
----
curl -H "X-Gravitee-Api-Key: $KEY" https://midpilot-api.evolveum.com/midpilot-connector-gen/api/v1/ready
----
+
The command must return HTTP 200.
    ** Verification: create a dummy CSV resource and request mapping suggestions, and generate a SCIM connector targeting link:https://scim.dev/[`scim.dev`].

* *Common to both self-hosted microservices*
    ** LLM endpoint is reachable from the microservices.
    ** LLM API key is valid.
    ** MidPoint and the microservices can communicate.

* *Smart resource integration (self-hosted)*
    ** `serviceUrl` in System configuration points to the correct microservice address and port.
    ** Verification: create a dummy CSV resource and request mapping suggestions.

* *Connector generator (self-hosted)*
    ** `connectorGenerationUrl` in System configuration points to the correct microservice address and port, including `/api/v1`.
    ** `connectorGeneratorApiKey` is set when the microservice runs with `AUTH__MODE=prod`.
    ** `connectorFrameworkUrl` and `connectorSqlFrameworkUrl` point to valid JAR files that midPoint can access.
        The JAR version matters.
    ** PostgreSQL is running, the database exists, the migration has run, and the microservice can connect.
    ** Search engine is configured and accessible by the microservice.
    ** `GET /api/v1/ready` returns HTTP 200.
    ** Verification: generate a SCIM connector targeting link:https://scim.dev/[`scim.dev`].
