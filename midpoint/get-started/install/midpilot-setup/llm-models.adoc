:page-description: Evaluation of smaller open-weight LLMs for the self-hosted midPilot connector generator microservice, compared with the GPT-OSS-120b baseline


The self-hosted xref:/midpoint/get-started/install/midpilot-setup/#connector-generator-microservice[connector generator microservice] works with any LLM that offers an OpenAI-compatible API (see xref:/midpoint/get-started/install/midpilot-setup/#llm-provider[LLM provider]).
The xref:/midpoint/get-started/install/midpilot-setup/#evolveum-hosted[Evolveum-hosted service] uses *GPT-OSS-120b*, and that model also serves as the baseline on this page.

A model of that size needs a data-center GPU.
Smaller open-weight models can run on less hardware, but they may produce worse connectors.
This page compares several smaller models with GPT-OSS-120b on the same applications and documentation, so you can decide which model fits your hardware and quality needs.

[NOTE]
====
The results apply to the connector generator only.
The xref:/midpoint/get-started/install/midpilot-setup/#smart-resource-integration-microservice[smart resource integration microservice] (mapping and correlation suggestions) was not evaluated on this page.
====

== Summary

None of the smaller models has a significantly lower F1 than GPT-OSS-120b in the digester, the part of the connector generator that analyzes the documentation: all differences in the overall F1 are within the uncertainty.
The models differ in the details: some leave expected object classes out, some list many object classes that the connector does not need, and some take much longer than the baseline.
Qwen3.6 35B-A3B comes closest to the baseline overall, finds every evaluated object class, and its generated Jira code scores higher than the baseline code, at the edge of significance.
Qwen3.8 27B has the highest digester score, but like Gemma 4 31B it leaves expected object classes out, and it is slower than GPT-OSS-120b on the same GPU server.
Qwen3.5 9B, the smallest evaluated model, has a digester F1 on par with the baseline, but it finds significantly fewer expected items, its generated code scores significantly lower than the baseline code, and it is very slow on local hardware.

.Reasoning settings
[NOTE]
====
The models differ in how their reasoning can be controlled:

* GPT-OSS-120b has the reasoning effort levels `low`, `medium`, and `high`.
    The evaluation used `high` (`LLM__REASONING_EFFORT=high`).
    The connector generator sends no reasoning effort by default, so set this variable to reproduce the evaluation.
* The Gemma 4 models, Qwen3.6 35B-A3B, and Qwen3.5 9B have no effort levels.
    They can only turn thinking on or off, and thinking was on.
* Qwen3.8 27B has its own effort levels: `xhigh` (the default), `medium`, and `low`.
    The evaluation used the default effort.
====

== How the models were evaluated

The connector generator first analyzes the API documentation of the application; this part is called the _digester_.
It finds the object classes (such as users, groups, or projects), their attributes, the API endpoints for each class, the authentication methods, and application metadata.
Then it generates the connector code from the results.

The evaluation measured both parts:

Digester::
Every result was compared with expected answers that engineers prepared by hand.
Four operations were scored: object classes, metadata, attributes, and endpoints.
The digester score is the overall score of these four operations.
Authentication and relations between object classes are not included (see the note below).

Generated connector code::
Each generated part of the connector ran inside the hand-written reference connector, against a mocked API of the application.
Its score shows how closely it behaves like the hand-written part, from 0 to 1.
The evaluated parts are the native schema, the searches (all objects, by ID, and by filter), and the create, update, and delete operations of each object class.
The authorization part is not included (see the note below).
Only OpenProject and Jira have a reference connector, so the code was evaluated for these two applications only.

The attributes, endpoints, and generated code were evaluated for the object classes in the _Object classes evaluated in detail_ column.
The object classes operation is scored against both columns: the connector needs the other expected object classes too, or it may need them (OAuthApplication, OauthClientCredentials, and ProjectStatus of OpenProject), but their attributes and endpoints were not evaluated.
OpenProject therefore has 13 expected object classes, Jira 5, Nextcloud 2, and Forgejo 5.

The documentation was downloaded manually and uploaded to the connector generator.
The documentation search (discovery) and download (scraper) of the connector generator were not used, to avoid problems caused by wrong or incomplete documentation.
The goal was to evaluate the digester and the code generation when the correct documentation is uploaded.

=== Repetition and documentation

The documentation of each application was uploaded to the connector generator once.
Every model read exactly the same documentation, so the differences between the models do not come from the documentation.

An LLM gives slightly different answers each time.
The digester and the code generation therefore ran *3 times* for each application and model, and the scores are means over these runs.

.Authentication, relations, and authorization are not included
[NOTE]
====
The digester score does not include two operations of the digester: authentication and relations between object classes.
The score of the generated code does not include the authorization part, which builds on the authentication output of the digester.
These parts will be evaluated later.
====

[[scores]]
=== Scores

Each run of an operation produces a set of items, for example the names of the object classes the model found.
The items are compared with the expected answers, and each item falls into one of three groups:

* *TP* (true positive): the model produced the item, and it is expected.
* *FP* (false positive): the model produced the item, but it is not expected.
    The model invented it, or it is not needed for the connector.
* *FN* (false negative): the item is expected, but the model did not produce it.

From these counts, four scores from 0 to 1 are computed:

[cols="1,2,4", options="header"]
|===
|Score |Formula |Meaning

|Precision
|`TP / (TP + FP)`
|How much of what the model produced is correct.
Low precision means that the model invents object classes, attributes, or endpoints that the application does not have, or lists more than the connector needs.

|Recall
|`TP / (TP + FN)`
|How much of what the model should have found it really found.
Low recall means that the model misses things.

|F1
|`2 × precision × recall / (precision + recall)`
|Precision and recall combined into one number.
F1 is high only when both are high.
This is the main score.

|Accuracy
|`TP / (TP + FP + FN)`
|The share of agreement between the produced and the expected items (the Jaccard index).
The evaluation compares sets of items, so there are no true negatives, and the usual accuracy formula does not apply.
Accuracy is always lower than or equal to F1, and it penalizes every wrong or missing item more strongly.
|===

A score with a zero denominator is 0.
A job that failed scores 0 on all four scores.

The items of each operation are the following:

[cols="1,4", options="header"]
|===
|Operation |Items compared with the expected answers

|Object classes
|Names of the object classes, case-insensitive.
Only the object classes that the connector needs or may need are expected (see <<applications>>), so precision is low when the model lists every object class the API has.

|Metadata
|Each field is one item: application name, application version, API version, API type, base API URLs and their type.

|Attributes
|Attributes of each object class, scored three ways and then averaged:
by name only, by name with type and format, and by name with all six flags (mandatory, updatable, creatable, readable, multivalued, returned by default).
An attribute found by name but with a wrong value counts as both FP and FN.

|Endpoints
|HTTP method and path of each endpoint of each object class, relative to the base API URL.
A path that also contains the base path, such as `/ocs/v2.php/cloud/users` instead of `/users`, or that names its path parameters differently, such as `{userid}` instead of `{userId}`, matches too.
|===

The expected answers were prepared by hand by engineers, so they are partly subjective.
Whether an object class is relevant for the connector is a matter of judgment, and another engineer might mark some object classes differently, which would change the scores slightly.
The most important object classes are those that identity management systems work with, such as users, groups, roles, organizations, teams, or similar object classes.

==== How the scores are combined

Every level is a plain mean, so every part has the same weight:

. The score of one operation for one object class is the mean of the 3 runs.
. The score of an operation is the mean over its object classes.
. The digester score of an application is the mean of its four operations.
. The score of a model is the mean over the applications.

Each score is averaged on its own.
F1 is computed in every run and then averaged, so the mean F1 is not the F1 of the mean precision and the mean recall.

[[uncertainty]]
=== Uncertainty (u95)

Every score has the form `mean ± u95`, for example `0.587 ± 0.070`.
The u95 value is the expanded uncertainty with about 95% confidence: the score of the model lies between `0.517` and `0.657` with about 95% probability.

The u95 of one operation for one object class comes from the 3 runs:

`u95 = k × k~s~ × s / √n`

where:

* `n` is the number of runs (3),
* `s` is the standard deviation of the scores of the runs,
* `k = 2` is the coverage factor for about 95% confidence,
* `k~s~` corrects for the small number of runs (`k~s~ = 2.3` for 3 runs).
    Together, `k × k~s~ = 4.6` approximates the Student's t factor for 2 degrees of freedom at the confidence of `k = 2` (95.45%), which is 4.53.

The u95 of a mean of `m` scores (over object classes, operations, or applications) combines their uncertainties as independent:

`u95 = √(u95~1~² + u95~2~² + … + u95~m~²) / m`

How to read u95:

* *A difference between two models is significant* only when it is larger than the combined uncertainty of both, `√(u95~A~² + u95~B~²)`.
    In the digester comparison, each u95 is at least the weight of one expected item, so a difference caused by a single item is not significant, even when it is larger than the combined u95 from the tables.
* *`± 0.000`* means that all 3 runs gave the same result.
    It does not mean that the score is exact: with 3 runs only, a rare different answer may simply not have occurred.
* *A u95 wider than the score range*, such as `0.552 ± 0.555`, means that the runs differed a lot.
    The model is unstable in that operation, and the mean alone says little.
* u95 covers the variation between the runs of the model on the same documentation.
    It does not cover other documentation, other applications, or errors in the expected answers.

=== Failed jobs

The share of jobs that failed, for example because the model returned output that the connector generator could not parse, or because a step had no input from the previous one.
For example, when the model leaves an object class out of the object classes, the attributes and endpoints of that class cannot be analyzed in that run.

The columns mean the following:

Codegen score::
The main score.
Each generated part runs in test scenarios, and its result and the requests it sends to the API are compared with the hand-written part, with partial credit.
The score is the mean over all parts; a part that the model did not generate, or could not generate because of a missing input, scores 0.
The u95 is computed in the same way as for the digester.

Score of the generated code::
The same score, but only over the parts for which the model generated code.
A large difference from the codegen score means that the model often produced no code at all.

Loads::
The share of the parts that the connector framework could load, as a mean over the parts.
A part without code counts as not loaded.
A part that does not load scores 0 in all its scenarios.

Passes exactly::
The share of test scenarios in which the generated part behaves exactly like the hand-written part, as a mean over the parts.

== Conclusion

In the digester, the evaluated smaller models can replace GPT-OSS-120b: none of them has a significantly lower overall F1.
They differ more in reliability than in the scores.
Models that leave expected object classes out lose the attributes, endpoints, and generated code of those classes, and some models take much longer than the baseline.
The generated code does not always follow the digester score.

In these results, Qwen3.6 35B-A3B comes closest to the baseline, followed by Gemma 4 26B-A4B. Try it on the applications that you need, because the results differ between applications.
